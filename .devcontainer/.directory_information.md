# `.devcontainer`

Devcontainer definition for super_projects.

| Path | Role |
|------|------|
| `Dockerfile` | Image build (tools, desktop/VNC, Chrome, mise, CLIs) |
| `compose.yaml` | Parent `devcontainer`, `localhost_forward_proxy` sidecar, named volumes, host agent + `known_hosts` mounts |
| `devcontainer.json` | IDE/CLI integration; `initializeCommand` / `postStartCommand` |
| `localhost-forwards.md` | How Compose `ports:` from stacks in the workspace become `http://localhost:<port>` in the parent Chrome / MCP |
| `scripts/` | Helpers by invocation site (`dockerfile/`, `shell/`, `localhost_forward_proxy/`) — see `scripts/.directory_information.md` |
| `persist/` | Dual-mount shortcuts + README for named-volume state (data lives in Docker volumes) |
| `.env.namespace_override.example` | Tracked copy-me template (`SUPER_PROJECTS_NAME=super_projects`, `SUPER_PROJECTS_WORKDIR=workspaces`). Copy to `.env.namespace_override`. |
| `.env.namespace_override` | User override (gitignored, never regenerated). Source of truth for `${SUPER_PROJECTS_NAME}` and `${SUPER_PROJECTS_WORKDIR}`; else they default to super_projects and workspaces respectively. |
| `.env` | Generated on the host by `initializeCommand` (gitignored, overwritten every initialize); bind-mount vars plus `SUPER_PROJECTS_NAME`, mirrored `COMPOSE_PROJECT_NAME`, and `SUPER_PROJECTS_WORKDIR`. Users do not edit the name or workdir here. |

## `localhost_forward_proxy` resource use and limits

How it works: [`localhost-forwards.md`](localhost-forwards.md). Stop or start it without restarting the devcontainer: `docker compose --project-directory .devcontainer -f .devcontainer/compose.yaml stop localhost_forward_proxy`.

Idle use is small: on the order of 20–25 MiB RAM and near-zero CPU. The sidecar is `docker-init`, a Ruby watcher, and a long-lived `docker events` child. Between a 15 second heartbeat and container start/stop events it sleeps. Byte copies (`IO.copy_stream`) do not buffer whole responses, so a large download does not grow the Ruby heap the way a buffering HTTP proxy would. That is the intended load: Chrome / chrome-devtools-mcp against a handful of published app ports.

CPU and RAM jump when Docker is busy, not when HTTP is busy. Each heartbeat, and each container start or die **anywhere on the same Docker daemon**, runs `docker ps` plus a full `docker inspect` of every running container (not only workspace ones). Those syncs take a mutex, so they run one after another. A compose `up`/`down` or many short-lived containers on Docker Desktop is the usual spike; a busy CI daemon on the same engine would chatter more. Each accepted TCP connection is two Ruby threads and two sockets until it closes (no idle timeout or cap). Thousands of leftover connections would add up; MRI still runs Ruby on one core.

Limits that follow from that design:

- TCP to `127.0.0.1` only. UDP (HTTP/3 / QUIC) is not mirrored, and it does not listen on `::1`.
- Fine for browser/dev traffic; not a high-throughput proxy.
- Inspect cost scales with every running container on the host, not with how many ports you publish.
- After `compose down`, the devcontainer stays on the app network (`Resource is still in use`) so the next `up` can reuse it. Stopping the sidecar drops `localhost:<port>` but does not undo that attach. Service-name URLs such as `http://sample_app_1/` are Docker DNS on a shared network, not the proxy.
- A port already bound in the devcontainer is skipped until the next sync (up to 15 seconds, or the next start/die event). Typical examples are noVNC (`6080`) and Chrome remote debugging (`9223`).
- `SIGTERM` is `exit` (open requests die; `compose stop` is fast). `docker inspect` has no timeout, so a stuck Docker API blocks sync until it returns.
