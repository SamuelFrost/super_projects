# `.devcontainer`

Devcontainer definition for super_projects.

| Path | Role |
|------|------|
| `Dockerfile` | Image build (tools, desktop/VNC, Chrome, mise, CLIs) |
| `compose.yaml` | `devcontainer` service, `localhost_forward_proxy` sidecar, named volumes. Bind mounts and project identity are not interpolated here. |
| `docker_compose_configuration_customizations/` | Docker Compose files loaded after `compose.yaml`. See `docker_compose_configuration_customizations/.directory_information.md`. |
| `devcontainer.json` | IDE/CLI integration; `initializeCommand` / `postStartCommand` |
| `scripts/` | Helpers by invocation site (`dockerfile/`, `shell/`, `localhost_forward_proxy/`) — see `scripts/.directory_information.md` |
| `lllm/` | Google Agent Development Kit agent. `lllm` streams a coordinator against the local Ollama server. It delegates browser work to Chrome DevTools and file work to workspace list, search, read, edit, and write tools. It does not run shell commands. |
| `desktop/` | AI CLI desktop/application-menu launchers and SVG icons |
| `persist/` | Dual-mount shortcuts + README for named-volume state (data lives in Docker volumes) |
| `privacy/` | AI reporting defaults and provider account training opt-out instructions |

The Dockerfile uses independent stages for CLI installers, Python dependencies,
and desktop package downloads. Apt installs desktop applications and system tools
in the runtime stage so dependencies and package hooks remain intact. The final
stage copies tool installations before adding launchers, privacy settings, and
startup scripts. BuildKit can build independent stages concurrently and reuse
their cached results when another installer or a startup script changes. Node is
downloaded once for the npm installer stages and final image; desktop package
installation does not depend on Node. Stages use the image target architecture
selected by the Compose architecture layer.
