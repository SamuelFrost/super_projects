# `.devcontainer/scripts/localhost_forward_proxy`

Ruby (stdlib only) sidecar that mirrors the published `ports:` of docker compose stacks in the workspace onto `127.0.0.1` in the devcontainer.

| Path | Role |
|------|------|
| `bin/localhost_forward_proxy` | Process entrypoint (Compose `command:`) |
| `lib/localhost_forward_proxy/watcher.rb` | Finds workspace stacks, attaches the devcontainer to their network so it can reach them, keeps one TCP proxy per published host port |
| `lib/localhost_forward_proxy/docker.rb` | Docker CLI wrapper (`ps`/`inspect`, `network connect`, `events`) |
| `lib/localhost_forward_proxy/tcp_proxy.rb` | `127.0.0.1:<hostPort>` → container IP:port byte copier |
| `Dockerfile` | Runtime image only (`ruby:4.0.7-alpine` + `docker-cli`); the code is bind-mounted from this directory |
| `.mise.toml` | Pins Ruby 4.0.7 for the tests (`mise test` from this directory) |
| `test/localhost_forward_proxy_test.rb` | Checks the sync rules against a fake Docker and the TCP proxy against a real socket |

Started by `.devcontainer/compose.yaml` as service `localhost_forward_proxy` with `network_mode: service:devcontainer` and the host Docker socket. User-facing guide: [`.devcontainer/localhost-forwards.md`](../../localhost-forwards.md).

```sh
docker compose --project-directory .devcontainer -f .devcontainer/compose.yaml logs -f localhost_forward_proxy
docker compose --project-directory .devcontainer -f .devcontainer/compose.yaml stop localhost_forward_proxy
docker compose --project-directory .devcontainer -f .devcontainer/compose.yaml start localhost_forward_proxy
```

The log lists active forwards as `<hostPort>→<container>:<privatePort>` whenever they change. Unit tests: `mise test` from this directory.

## How it works

On container start/stop events, and every 15 seconds, the watcher inspects running containers whose Compose `working_dir` is under the workspace (`/${SUPER_PROJECTS_WORKDIR:-workspaces}` inside the container, or `HOST_WORKSPACE_DIR` on the host), skipping the devcontainer's own Compose project.

It attaches the `devcontainer` to that stack's Compose network when it is not on it yet, so the sidecar can reach the container's private IP. Sharing a network also lets Compose DNS names resolve (for example `http://sample_app_1/`); that is Docker networking, not the proxy.

It listens on `127.0.0.1:<hostPort>` for each published **TCP** port and copies the byte stream to the container's private port. UDP is not mirrored. The sidecar shares the devcontainer's network namespace, so Chrome in the devcontainer sees those listeners as its own localhost. HTTPS, HTTP/2 over TCP, and WebSockets work because the proxy does not interpret the stream. HTTP/3 / QUIC does not, because it is UDP.

## Resource use and limits

Idle use is small: on the order of 20–25 MiB RAM and near-zero CPU. The sidecar is `docker-init`, a Ruby watcher, and a long-lived `docker events` child. Between a 15 second heartbeat and container start/stop events it sleeps. Byte copies (`IO.copy_stream`) do not buffer whole responses, so a large download does not grow the Ruby heap the way a buffering HTTP proxy would. That is the intended load: Chrome / chrome-devtools-mcp against a handful of published app ports.

CPU and RAM jump when Docker is busy, not when HTTP is busy. Each heartbeat, and each container start or die **anywhere on the same Docker daemon**, runs `docker ps` plus a full `docker inspect` of every running container (not only workspace ones). Those syncs take a mutex, so they run one after another. A compose `up`/`down` or many short-lived containers on Docker Desktop is the usual spike; a busy CI daemon on the same engine would chatter more. Each accepted TCP connection is two Ruby threads and two sockets until it closes (no idle timeout or cap). Thousands of leftover connections would add up; MRI still runs Ruby on one core.

Limits that follow from that design:

- TCP to `127.0.0.1` only. UDP (HTTP/3 / QUIC) is not mirrored, and it does not listen on `::1`.
- Fine for browser/dev traffic; not a high-throughput proxy.
- Inspect cost scales with every running container on the host, not with how many ports you publish.
- After `compose down`, the devcontainer stays on the app network (`Resource is still in use`) so the next `up` can reuse it. Stopping the sidecar drops `localhost:<port>` but does not undo that attach. Service-name URLs such as `http://sample_app_1/` are Docker DNS on a shared network, not the proxy.
- A port already bound in the devcontainer is skipped until the next sync (up to 15 seconds, or the next start/die event). Typical examples are noVNC (`6080`) and Chrome remote debugging (`9223`).
- `SIGTERM` is `exit` (open requests die; `compose stop` is fast). `docker inspect` has no timeout, so a stuck Docker API blocks sync until it returns.
